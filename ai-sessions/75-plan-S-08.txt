  The plan is in context/changes/list-pagination/plan.md. The API already
  supports limit and offset, so this is a web-only change.

  Your decisions:
  - The page goes in the URL as page=N; page 1 is left out.
  - Previous / Next buttons with a "Page X of Y" label.
  - A page past the end replaces the URL with the last page, without adding a
    history entry.
  - Two phases, with no new Playwright test.

  Decisions I made from the code:
  - Pages are fixed at 20 rows.
  - The pagination bar only appears when there are more than 20 matches.
  - Changing a filter or the sort goes back to page 1.
  - Clicking Apply without changing the filters keeps the current page. This
    changes how Apply decides whether to navigate: it now compares only the
    filters, not the whole URL.
  - An invalid page value (0, abc, more than 6 digits) is ignored and page 1
    shows.

  Phases:
  1. Page in the URL module: list-search.ts reads and writes page, proven by
     unit tests. Also adds the TR-27 test-plan row.
  2. Paged list: useProperties sends limit and offset, followed by pnpm codegen.
     ListPage gets the pagination bar, the reset to page 1 and the past-the-end
     handling. Component tests cover each case, and the existing exact-request
     assertions now expect limit: 20, offset: 0.
