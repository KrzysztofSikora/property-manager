● The plan review for create-property-with-weather is done. The verdict is ready
  with notes: nothing blocks it, but three major issues should be fixed before
  /implement. plan.md hasn't been changed.

  Major
  1. The API package doesn't depend on the shared package. The plan imports from
     @property-manager/shared starting in Phase 1, but apps/api/package.json
     doesn't list it, so Phase 1's typecheck would fail. Fix: add
     "@property-manager/shared": "workspace:*" in Phase 1.
  2. The error-masking rule would hide validation errors. In graphql 17, an
     error thrown by a resolver arrives wrapped around the original. As written,
     the rule ("pass through only if there's no inner error") would turn every
     BAD_USER_INPUT into INTERNAL_SERVER_ERROR. The plan should look through the
     wrapping the way Yoga's own check does, and add unit tests that build
     errors with locatedError.
  3. The weather mapper would drop out of mutation testing. The plan moves it to
     domain/weather.ts, but test-plan.md:113 only covers
     adapters/weatherstack/. Fix: add the new file to the mutation list and
     update that line of the test plan.

  Minor
  4. With z.preprocess, the AddressInput fields come out typed as unknown, and
  refine doesn't narrow state to StateCode. Chaining trim/overwrite/toUpperCase
  instead keeps them typed as strings.
  5. FR-05 AC6 ("the database rejects the save") is only tested with a fake
  repository that throws. A real check is cheap: a fake weather response with
  lat: "999" breaks the properties_lat_range constraint.
  6. The domain-error mapping keeps path but drops nodes/positions, so those
  errors lose locations.
  7. Regenerating the web client output will type the JSON/DateTime scalars as
  any. Lint ignores that folder, so S-04 could pick up any without anyone
  noticing.

  The review also confirmed the file and line references in the plan,
  graphql-scalars@2.0.0 working with graphql 17, a test for every in-scope
  acceptance criterion, phases in dependency order, and the Stryker concurrency
  rule from lessons.md.

● I've updated context/changes/create-property-with-weather/plan.md to fix all
  seven review findings. These are plan edits only; I haven't run any code or
  tests, and nothing is committed (the change folder is still untracked).

  Major
  1. Missing shared dependency: Phase 1 now adds "@property-manager/shared": 
     "workspace:*" to apps/api/package.json, runs pnpm install and updates the
     lockfile.
  2. Error masking:
     - The Yoga finding, the error-model decision and the createMaskError design
       now account for graphql 17 wrapping resolver-thrown errors.
     - createMaskError follows the chain of inner errors to the first one that
       isn't a GraphQLError. A domain error becomes its own error code, a chain
       that ends in a GraphQLError (such as a validation error) passes through
       unchanged, and anything else is masked.
     - The Phase 4 unit tests build their errors with locatedError(...): a
       wrapped validation error, a wrapped domain error and a wrapped plain
       Error.
  3. Weather mapper: domain/weather.ts is now in the mutation-target list, and
     the Phase 4 edit to test-plan.md updates the row at line 113 to name it.

  Minor
  4. Address schema: street and city use
  z.string().trim().overwrite(normalizeAddressText), so every AddressInput field
  stays typed as string. For state I didn't use either of the review's
  suggestions. It uses a .transform built on the existing isStateCode type
  guard, which narrows the output to StateCode without a cast or a new export
  from states.ts.
  5. Real database rejection: Phase 4 adds an integration test where a fake
  weather response with lat: "999" breaks the properties_lat_range check. It
  expects INTERNAL_SERVER_ERROR, no stored row, and no constraint name or SQL in
  the response.
  6. Error locations: domain errors now keep nodes, source, positions and path
  from the outer error, so they keep locations.
  7. Web scalars: the web client output in codegen.ts gets JSON: 'unknown' and
  DateTime: 'string', so no any reaches S-04.

  I also added a line under Risks and unknowns saying the review's findings are
  applied. The next step is /implement when you're ready.
