● I wrote the test plan to context/test-plan.md. I haven't committed it.

  What's in it
  - Risk register: 25 risks, ranked by impact × likelihood. The top ones are:
    - the Weatherstack key leaking into logs, URLs or errors;
    - Weatherstack errors sent as HTTP 200 with success: false being treated as
      success;
    - responses with a changed or partial shape getting stored;
    - Weatherstack calls that shouldn't happen (wasted quota);
    - failed creates leaving a partial row.

    Each risk has a test level (unit, integration or e2e) and the tests that
    cover it.
  - Test names: every test starts with its AC ID (e.g. FR-07 AC1: …), so you can
    check with grep that every Must AC has a test (success criterion 7).
  - Not tested: real Weatherstack calls, the real 5-second timeout,
    Weatherstack's geocoding accuracy, the libraries themselves, styling, load,
    migration rollback, the README and AI deliverables (checked by checklist),
    and the Should/Could items.
  - Mutation targets: six modules, with target scores from 80% to 100%:
    - the shared address schema;
    - the Weatherstack adapter's response parsing and error mapping;
    - the key-redaction helper (100%);
    - the create flow and region check in the service;
    - GraphQL error mapping and the properties query arguments;
    - the web's mapping of API errors to UI messages.

    Stryker stays out of CI, as the roadmap decided. The fail threshold stays
    off until the first run records a baseline. The repository's SQL isn't a
    target, because only database tests cover it and running those once per
    mutant would be too slow.
  - Cookbook: step-by-step recipes for unit, integration, e2e and mutation
    tests, with file locations and helper names.

  New decisions to confirm. These aren't in the tech stack or roadmap yet:
  1. Pre-commit hook: a plain .githooks/pre-commit script, turned on through
     core.hooksPath, with no husky or lefthook dependency. It runs lint,
     typecheck, the unit tests and a scan for the key in staged changes (it
     never prints the key).
  2. Editor hook: a Claude Code PostToolUse hook that runs Prettier and ESLint
     on each edited file.
  3. Test layout: integration tests are named *.int.test.ts, so the Stryker
     config can leave them out. The database tests use one Testcontainers
     PostgreSQL container per run and run one file at a time.
  4. Timeout test: the adapter gets an injectable timeout, so the test can use a
     short one and doesn't wait 5 seconds.
  5. Codegen check in CI: CI regenerates the GraphQL types and fails if they
     differ from the committed files.

  Items 1–3 and 5 belong in the F-01 scope, and item 4 in S-02's. The helper
  names (createTestApp, FakeWeatherClient.withBarrier, expectNoSecret, …) are
  what I intend; no code exists yet. The F-01, F-02 and S-01 plans should update
  this file if any name or path changes.

  Next step: /plan repo-skeleton.
