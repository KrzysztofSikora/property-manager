● I wrote the plan for FR-12 AC6 to
  context/changes/details-extra-weather/plan.md. It needs a roadmap ID, so I
  added a new row, S-09, to context/roadmap.md with status planned. The row

  Your decisions:
  - Where the fields come from: typed fields in the GraphQL schema rather than
    the web reading raw. That means this change also delivers #12 (typed non-key
    weather fields), and its one commit closes both issues.
  - Air quality: all 8 values, with the US EPA index labelled, e.g. "1 (Good)".
  - Observation time: shown as stored plus "UTC", e.g. "01:13 PM UTC". The
    recorded sample proves it's UTC: 01:13 PM against a local time of 06:13 at
    UTC−7. It has no date, so converting it to local time isn't safe.
  - Phases: one phase, one commit.

  Design points from the research:
  - Create is unaffected. The Weatherstack adapter reuses the key-field schema,
    so the new optional fields get their own parsing that never throws. A wrong
    or missing value becomes null for that field only and never fails a create
    or a read.
  - Separate groups on the page. The existing details test compares every
    label/value pair in one list, so the new data goes in three separate groups:
    "Weather details", "Astronomy" and "Air quality". A group with no values is
    left out.
  - Zero still shows. Values like UV index 0 and precipitation 0 are displayed,
    not hidden, and a test checks this.
  - Air-quality numbers arrive as numeric strings. They're parsed with the same
    decimal check already used for lat/long, because a plain number conversion
    would turn "" into 0.

  One open risk: I couldn't confirm the pressure and visibility units ("mb" and
  "mi"). The Weatherstack docs site loads its content with JavaScript, so it
  came back empty. They come from Weatherstack's unit table as I remember it;
  the PRD confirms only inches for precipitation. It doesn't block anything
  since only two labels change if wrong, and checking them in a browser is
  listed as a manual check in the plan.

  1. Major: two existing API tests would fail, and the plan doesn't name them.
     - apps/api/test/integration/property-repository.int.test.ts:62 compares the
       stored weather against an object with only the key fields and raw, so
       the new fields break it.
     - apps/api/test/operations.ts has no separate details operation. It is one
       field selection shared by create, details and list. Adding fields there
       also changes the create response, which breaks the full-object check at
       create-property.int.test.ts:75.
     - Fix: add both files to Phase 1, say the selection is shared, and recheck
       query-properties.int.test.ts for the same kind of check.
  2. Minor: null and undefined are mixed up. The domain and its unit tests
     should say undefined; null applies only in GraphQL and the web. The
     weather.test.ts bullet currently says null.
  3. Minor: the new mapping test is too loose. The existing test uses
     toMatchObject, which wouldn't catch an extra or misnamed field. The new
     sample test should use toEqual on the typed fields.
  4. Minor: the units are still unconfirmed. The reviewer couldn't confirm "mb"
     and "mi" either. The browser check against the Weatherstack docs should
     happen before the commit, not after.
