  Your decisions
  - What goes in the URL: the filters and the sort, as
    ?city=…&state=AZ&zip=85268&sort=asc. Blank values and the default "Newest
    first" are left out.
  - History: each Apply and each sort change adds a history entry, so browser
    Back brings back the previous filters.
  - Bad URL values: a value like state=XX, sort=foo or a value that's too long
    is ignored on its own field. The URL itself is left as it is.

  Phases
  1. New file apps/web/src/lib/list-search.ts: it reads the list state from the
     URL and writes it back, checked with zod. A unit test table covers the
     rules, with one invalid field per case as lessons.md requires. test-plan.md
     gets a new risk row, TR-26, and lists this file as a mutation-test target.
  2. ListPage uses the URL: it reads and writes the filters and sort through
     useSearchParams. The filter form is rebuilt whenever the URL changes, so
     the inputs show the URL's values after a reload and after Back.
     - ListPage tests: writing the URL, opening a URL with filters, Back, and an
       invalid state.
     - Playwright: the journey gets a reload step after the city filter.

  One behaviour change: changing the sort throws away city or zip text you typed
  but didn't apply. Only applied filters ever affected the list, so this keeps
  the inputs matching the URL. The Phase 2 human check covers it.
