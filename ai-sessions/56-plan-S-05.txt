● I wrote the plan to context/changes/create-property-page/plan.md and set S-05
  to planned in context/roadmap.md. Nothing is committed yet.

  Your decisions:
  - State field: a text input checked by the shared schema. Lowercase is
    accepted, and XX gets a message next to the field, as FR-13 AC1 and TR-21
    say.
  - Error messages: the form takes them from a client table in
    lib/graphql-errors.ts, one per error code. The exception is
    WEATHER_LOCATION_MISMATCH: the form shows the API's message, because only
    the API knows which state Weatherstack returned.
  - Validation timing: checks run only when the form is submitted.

  Things the research settled:
  - No React 19 form action. It clears the inputs after a submit, which would
    break AC3 ("keeps the entered values"). The form uses onSubmit instead, like
    ListPage.
  - Messages per field: zod 4's z.flattenError turns failed checks into one
    message per field.
  - Server field errors: the field messages the API sends with BAD_USER_INPUT
    are parsed with zod. If they are missing or malformed, the form shows a
    single message at the top instead.
  - Empty result: if the API returns createProperty: null, the form treats it as
    an error, so it never navigates to /properties/null.
  - After success: the hook refreshes the list's cached data and the page
    navigates to the new property, the same split as delete.

  Phases:
  1. Error messages and hook: the message table, the reader for the API's field
     errors, and the useCreateProperty hook, proven by unit tests (TR-19).
  2. Create page: the form itself, with Testing Library + MSW tests for FR-13
     AC1–AC4 (TR-19, TR-21). This phase also marks TR-19 and TR-21 as covered in
     the test plan.

  As the test plan says, S-05 has no Stryker step.
