  What you decided
  - Filter values: only a length cap, no format checks. A state like "Arizona"
    or a partial zip just matches nothing, the same way FR-03 AC3 treats a
    partial zip.
  - List results and total: the page of results and totalCount come from two
    queries in one read-only, repeatable-read transaction, so they always agree.
  - Argument validation: the zod schema for the properties arguments lives in
    the API, in apps/api/src/graphql/properties-args.ts.
  - Phases: the sort/paging and filter phases are merged into one.

  What I settled from the PRD, roadmap, docs and lessons
  - Filter cap: I set it to 100 characters for city, state and zip alike, so
    there's one rule. A longer value returns BAD_USER_INPUT. Change it if you
    want per-field caps.
  - Filter matching: the city filter is trimmed and its spaces collapsed, the
    same way stored cities are. It's a case-insensitive contains match, with %,
    _ and \ treated as plain characters.
  - null arguments: an explicit null counts as "not given", so the defaults
    apply.
  - Malformed id on delete: deleteProperty returns PROPERTY_NOT_FOUND without
    calling the service.
  - Service tests: list gets no service unit test because it only passes the
    query through; the integration tests prove it. delete gets one, because the
    service is what turns a missing row into the not-found error.

  Phases
  1. properties with sort, paging and filters: the schema, the argument schema
     with a unit table, and the repository query with the escaping helper.
     Integration tests cover FR-01, FR-02, FR-03 and the related test-plan risks
     (TR-13, TR-14), and check for zero weather calls.
  2. Property details tests and deleteProperty: the new not-found error and the
     repository delete. Integration tests cover FR-04, FR-09, FR-08 AC3 through
     the API, and malformed or unknown ids (TR-15). The test plan is updated in
     this phase.
