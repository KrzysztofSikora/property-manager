Property Manager: instrukcja implementacji

GraphQL API i frontend w React do zarządzania nieruchomościami. Przy tworzeniu nieruchomości aplikacja pobiera aktualną pogodę z Weatherstack. Całość budujemy w podejściu AI-first, z własnymi skillami w Claude Code.

  • 17–26 h+ 15–20% bufora
  • 10 skilliw .claude/skills/
  • 8 elementów3 fundamenty, 5 slice'ów
  • 1 repopubliczne, z sesjami AI

Cel i kryteria oceny

Encja Property ma pola id, city, street, state (skrót, np. AZ), zipCode (5 cyfr), weatherData (obiekt current z Weatherstack), lat i long. API pozwala wylistować nieruchomości, posortować je po dacie utworzenia, filtrować po mieście, kodzie i stanie, pobrać szczegóły, dodać i usunąć. Weatherstack wywołujemy tylko w mutacji tworzącej nieruchomość.

Stack narzucony przez firmę to TypeScript/Node na backendzie i React/TypeScript na frontendzie. Bazę danych wybieramy sami.

Rekruter oceni:

  • jakość kodu: code smells, wzorce, standardy, złożoność;
  • dobór technologii i bibliotek;
  • kompletność zakresu;
  • jakość zestawu narzędzi AI i promptów. Tę część oceny budują skille, artefakty w context/ i opublikowane sesje.

Proces w skrócie

Każdy krok zostawia plik w context/, który czyta następny krok. Dzięki temu decyzje nie giną razem z sesją, a rekruter widzi tok rozumowania obok kodu.

brief→/shape→/prd→/tech-stack→/roadmap→/test-plan

Dla każdego elementu roadmapy (change-id):

/plan→/plan-review→/implement⟲ każda faza→/mutation→/review→poprawki + lessons

Wszystkie skille uruchamiasz ręcznie, Claude nie wywoła ich sam. Zatwierdzasz stack, podział na fazy, każdą fazę i każdy commit. /plan-review i /review działają w osobnym kontekście, więc recenzent nie przejmuje założeń autora.

0Przygotowanie środowiska

Czas: 1–2 h. Skille są już gotowe w property-manager/.claude/skills/.

  1. Repozytorium

    cd ~/projects/taskTreeCover/property-manager
git init -b main
cp ../spectreecover docs/brief.txt

  2. Klucz Weatherstack i sprawdzenie planu

    Załóż darmowe konto i od razu sprawdź, czy Twój plan obsługuje HTTPS. Darmowe plany zwykle odrzucają HTTPS błędem 105 i mają mały miesięczny limit zapytań.

    curl -s "https://api.weatherstack.com/current?access_key=$WEATHERSTACK_KEY&query=85268" | head -c 400

    Klucz trzymaj w .env (dodanym do .gitignore), a w repo zostaw tylko .env.example.

  3. CLAUDE.md

    Krótki, najwyżej 60–80 linii. Opisz w nim:

    • stack i strukturę monorepo;
    • komendy: pnpm dev, test, typecheck, lint;
    • konwencje: warstwy resolver → service → repository/adapter, walidacja zod na wejściu, brak any;
    • zakazy: żadnych sekretów w kodzie i żadnych prawdziwych wywołań Weatherstack w testach;
    • odnośniki do context/prd.md, tech-stack.md i lessons.md.

    Uzupełniaj go po /tech-stack i F-01.

  4. Serwery MCP (.mcp.json)

    {
  "mcpServers": {
    "context7":   { "command": "npx", "args": ["-y", "@upstash/context7-mcp"] },
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] }
  }
}

  5. Hook z typecheckiem (.claude/settings.json)

    Dodaj go po F-01, kiedy istnieje już skrypt typecheck. Kod wyjścia 2 przekazuje błędy z powrotem agentowi, więc sam je poprawi.

    {
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "pnpm -s typecheck 1>&2 || exit 2" }]
    }]
  }
}

1Od briefu do roadmapy

Czas: 2–3 h. Uruchamiaj kroki po kolei w jednej sesji. Między krokami możesz zrobić /clear, bo wszystko jest w plikach.

  1. /shape wywiad

    /shape docs/brief.txt

    Wynik: context/shape-notes.md z decyzjami, założeniami, non-goals i ryzykami.

    Decyzje, które warto podjąć tutaj:

    • co wysyłamy do Weatherstack: pełny adres czy sam zip;
    • co robimy, gdy Weatherstack nie odpowiada: odrzucamy mutację czy zapisujemy bez pogody;
    • czy filtry są dokładne, czy częściowe i bez rozróżniania wielkości liter;
    • czy potrzebna jest paginacja;
    • czy usuwanie jest trwałe, czy miękkie.

  2. /prd

    /prd

    Wynik: context/prd.md z wymaganiami FR i kryteriami Given/When/Then oraz tabelą, która wiąże każdy punkt briefu z wymaganiem.

  3. /tech-stack akceptacja

    /tech-stack

    Wynik: context/tech-stack.md z porównaniem opcji, najmocniejszym argumentem przeciw każdemu wyborowi i wersjami sprawdzonymi w context7.

    Spodziewany wynik:

    • monorepo na pnpm workspaces;
    • backend: GraphQL Yoga lub Apollo Server, schema-first z graphql-codegen;
    • baza: PostgreSQL w Dockerze, Prisma lub Drizzle, walidacja zod;
    • frontend: Vite, React, Apollo Client lub urql z typowanymi hookami;
    • testy: Vitest i MSW, do E2E Playwright.

  4. /roadmap

  5. /test-plan

    /test-plan

    Wynik: context/test-plan.md z rejestrem ryzyk, poziomami testów, bramkami jakości i instrukcjami, jak dodać każdy rodzaj testu.

3Pętla dla każdego elementu roadmapy

Powtórz ją dla F-01, F-02, S-01 i kolejnych. Tam, gdzie jest napisane „akceptacja”, decyzję podejmujesz Ty.

  1. /plan akceptacja

    /plan S-01
    • Najpierw research: kod przez subagenta Explore, dokumentacja przez context7.
    • Potem najwyżej 6 pytań o decyzje, z sugerowaną odpowiedzią.
    • Zatwierdzasz listę faz, dopiero potem powstaje pełny plan.
    • Każda faza ma sprawdzenia agenta (komendy) i sprawdzenia, które robisz Ty.

    Wynik: context/changes/<change-id>/plan.md

  2. /plan-review

    /plan-review create-property-with-weather

    Działa w świeżym kontekście i kończy się werdyktem READY, READY WITH NOTES albo NEEDS CHANGES. Jeśli plan wymaga zmian, popraw go przez /plan w trybie edycji.

  3. /implement, jedna faza na uruchomienie akceptacja

    /implement create-property-with-weather

    Co dzieje się w każdej fazie:

    • agent pisze test, który najpierw nie przechodzi, i dopiero potem kod;
    • uruchamia sprawdzenia, typecheck i lint;
    • czeka, aż wykonasz swoje sprawdzenia;
    • proponuje commit feat(<change-id>): … i robi go po Twojej akceptacji, dodając pliki po nazwie;
    • dopisuje hash commita do sekcji Progress w planie.

    Gdy kontekst robi się długi, zrób /clear przed następną fazą.

  4. /mutation

    /mutation create-property-with-weather

    Stryker mutuje tylko krytyczną logikę zmiany: walidację, adapter Weatherstack, mapowanie błędów i budowanie filtrów. Używa szybkich testów bez bazy i sieci. Każdy mutant, który przeżył, dostaje jedną decyzję:

    • strengthen: dopisujemy asercję na zachowanie;
    • equivalent: mutacja nie zmienia niczego obserwowalnego;
    • accept: test byłby lustrem implementacji;
    • bug: kod produkcyjny jest już błędny, więc sprawa idzie do Ciebie.

    Kod produkcyjny pozostaje nietknięty. Po dopisaniu asercji Stryker uruchamia się ponownie.

    Wynik: context/changes/<change-id>/mutation.md z wynikiem przed i po. Pomijasz ten krok dla F-01, F-02 i slice'ów czysto UI.

  5. /review akceptacja

    /review create-property-with-weather

    Review działa w świeżym kontekście i robi trzy rzeczy:

    • porównuje plan z diffem: done, diverged, absent, unplanned;
    • ocenia 6 obszarów jako ok, concern albo fail;
    • zgłasza najwyżej 10 potwierdzonych znalezisk R1….

    Potem w głównej sesji decydujesz o każdym znalezisku: fix, defer, reject albo make it a rule. Ta ostatnia opcja dopisuje regułę do context/lessons.md, a kolejne skille będą jej przestrzegać.

Zapisuj sesje na bieżąco. Po każdym zakończonym elemencie roadmapy wyeksportuj sesję (/export) do ai-sessions/. Na koniec trudno odtworzyć kolejność pracy.

Testy i quality gates

Brief nie wymaga testów ani quality gates wprost. Ocenia jednak „coding standards and best practices” i jakość zestawu narzędzi AI, więc testy i automatyczne bramki są oczekiwane domyślnie. To również najmocniejszy dowód, że kod napisany przez AI został zweryfikowany. Ostateczny kształt ustali /test-plan. Poniżej punkt startowy.

Co testujemy i na jakim poziomie

PoziomZakresNarzędzia
UnitWalidacja wejścia (stan, zip, puste pola), mapowanie odpowiedzi Weatherstack (stringi na liczby, lon na long), mapowanie błędów, w tym success: false i timeoutVitest

Test sprawdza też, że zapytania nie wywołują pogody.Vitest, yoga.fetch lub supertest, MSW, Postgres z docker-compose lub Testcontainers

Testy mutacyjne (Stryker)

Pokrycie kodu mówi tylko, że kod wykonał się w testach. Testy mutacyjne sprawdzają, czy asercje zauważyłyby błąd. Stryker wprowadza drobne celowe usterki, np. > zamiast >= albo odwrócony warunek, i uruchamia testy. Mutant, który przeżył, to miejsce, którego nie pilnuje żadna asercja. AI rzadko zostawia kod niepokryty, ale często pokryty tylko pozornie, dlatego to dobra bramka dla testów pisanych przez agenta.

  • Zakres: tylko pakiet api, katalogi z logiką (walidacja, serwisy, adapter, mapowanie błędów). Pomijamy resolvery, kod z codegenu i konfigurację.
  • Szybkie przebiegi: osobny vitest.unit.config.ts z testami bez bazy i sieci, analiza pokrycia per test oraz tryb przyrostowy.
  • Próg: na start break: null. Po pierwszym /mutation ustal bazowy wynik, np. 70%, i dopiero wtedy włącz go w CI.
  • Wynik to wskazówka, nie cel. Liczą się decyzje o każdym mutancie, który przeżył, zapisane w mutation.md. Nie gonimy 100%.

Szkic konfiguracji. /mutation sprawdza aktualne nazwy opcji w context7 przed zapisaniem:

// apps/api/stryker.config.json
{
  "$schema": "./node_modules/@stryker-mutator/core/schema/stryker-schema.json",
  "packageManager": "pnpm",
  "testRunner": "vitest",
  "plugins": ["@stryker-mutator/vitest-runner"],
  "vitest": { "configFile": "vitest.unit.config.ts" },
  "coverageAnalysis": "perTest",
  "mutate": [
    "src/domain/**/*.ts", "src/services/**/*.ts", "src/weather/**/*.ts",
    "!src/**/*.test.ts", "!src/generated/**"
  ],
  "ignoreStatic": true,
  "incremental": true,
  "incrementalFile": "reports/stryker-incremental.json",
  "reporters": ["clear-text", "progress", "html", "json"],
  "htmlReporter": { "fileName": "reports/mutation/index.html" },
  "jsonReporter": { "fileName": "reports/mutation/mutation.json" },
  "thresholds": { "high": 85, "low": 70, "break": null }
}

Dopisz do CLAUDE.md krótki akapit swoimi słowami: Stryker działa tylko na celach z sekcji Mutation targets w test planie, przebiegi są zawężone (--mutate), a mutanty, które przeżyły, rozpatrujemy pojedynczo i nie poprawiamy kodu produkcyjnego pod mutanty.

Próg pokrycia kodu testami można ustawić tylko dla warstwy serwisów i adapterów, np. 80%. Nie ma sensu liczyć go globalnie, bo pokrycie nie jest celem samym w sobie. Zielony badge CI w README to prosty, widoczny sygnał dla rekrutera.
