# Plan review: create-property-page

Verdict: READY WITH NOTES

| # | Severity | Check | Finding | Suggested change |
|---|----------|-------|---------|------------------|
| 1 | major | Design / Failure paths | `maxLength` on inputs does not "never silently truncate". The plan says *"`maxLength` values equal the schema limits after trimming, so a value the browser accepts can still fail only on emptiness or format, never silently truncate"*. Browsers cut pasted text to `maxLength` without telling the user, so a pasted `852681` becomes `85268` and passes `^[0-9]{5}$` (`packages/shared/src/address.ts:34`). A property is then created with the wrong zip and no message, and FR-13 AC1 ("a zip that is not 5 digits … shows a field-level message") is skipped. A pasted state like ` az` (with a leading space) is also cut before the schema's `.trim()` (`address.ts:24`) can run. | Drop `maxLength` on Zip code and State, and let `addressSchema` report "must be 5 digits" / "must be a 2-letter US state code". If Street and City keep `maxLength`, say that they truncate. Optionally add an AC1 case with a 6-digit zip. |
| 2 | minor | Grounding | The plan says *"`onUnhandledFrame: 'error'` fails a test that sends an unhandled operation"*. The MSW docs say the `'error'` strategy prints an error and **rejects the in-flight request** (mswjs/msw `_autodocs/api-reference/experimental.md`, "UnhandledFrameHandle"). The test does not fail on its own: `execute` gets a fetch rejection and the page shows the generic message. The recorder handler is the real guard, and once it is installed the request is handled, so `onUnhandledFrame` never fires. | Rewrite *Test support* / *Risks* so the zero-call recorder is named as the assertion. Don't present `onUnhandledFrame` as a guard here. |
| 3 | minor | Grounding | *"`renderWithProviders` (`test/render.tsx`) uses a `MemoryRouter` with one route"*. It wraps `ui` in a `MemoryRouter` with no `<Routes>` (`apps/web/src/test/render.tsx:10-12`). It does not expose its `QueryClient` either, so the hook test has to build its own client, as `useDeleteProperty.test.tsx:15` does. | Fix the wording. Pass `<Routes>…</Routes>` as `ui` for the redirect test. |
| 4 | minor | Design | `ERROR_MESSAGES` has a generic name but holds create-specific text: `INTERNAL_SERVER_ERROR`: *"…the property was not saved"*, and `WEATHER_*` / `PROPERTY_ALREADY_EXISTS` are also create-only. `PROPERTY_NOT_FOUND` has the S-04 delete wording, but the plan keeps `DeletePropertyDialog` on its own strings, so that entry is unused. | Either name it for create (e.g. `CREATE_ERROR_MESSAGES`, still `Record<ErrorCode, string>` for TR-19), or make the generic entry context-free ("Something went wrong. Try again."). Note that `PROPERTY_NOT_FOUND` exists only to make the record complete. |

| 6 | minor | Failure paths | *"entries for unknown fields are ignored"*. When `BAD_USER_INPUT` names one known field and one unknown field, the unknown one disappears, and no form-level message is shown because "at least one field matched". Unlikely with the current API (`badUserInput` uses only the four arg names, `apps/api/src/graphql/errors.ts:13-25`), but the fallback is defined only for the all-unknown case. | Accept and say so in *Decisions*, or show the table message at form level whenever any entry was dropped. Covering this is a one-line change in the existing `fieldErrors` "unknown field" test. |

## What is good

- It traces cleanly. Each of FR-13 AC1–AC4 and TR-19 / TR-21 has a named test in Phase 2, and the TR-19 mapper table (`it.each(ERROR_CODES)` plus `Record<ErrorCode, string>`) is the guard `context/test-plan.md:79-81` asks for in place of `/mutation`.
- The citations check out. `schema.graphql:95`, the `BAD_USER_INPUT` shape (`errors.ts:13-25`), the mismatch message text (`domain/errors.ts`), `errorCode`, the `ListPage` `onSubmit` + `FormData` pattern (`ListPage.tsx:33-41`), the routes test heading, and the `useDeleteProperty` invalidation pattern are all real and quoted correctly.
- The research is sound. Using `onSubmit` instead of `<form action>` (React 19 resets the form) protects AC3's "values kept". Throwing on a `null` result avoids navigating to `/properties/null`. Since `execute` lets `{ createProperty: null }` through (`execute.ts:33-36`), that check really is needed.
- The layering matches the existing split: the hook owns the cache, the page owns navigation, and `extensions.fields` is zod-parsed at the boundary, as CLAUDE.md requires.
- Each phase can be verified on its own and has runnable checks. The human checks cover the real Weatherstack path and keyboard use. The scope stays tight: no API change, no change to the delete dialog, no e2e.
- It follows the lessons: tests assert the returned message and code, not only that something is present.
