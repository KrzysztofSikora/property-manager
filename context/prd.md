# PRD: Property Manager

Sources: brief `docs/brief.txt`, shape notes `context/shape-notes.md` (IDs C-, D-, A-, NG-,
Q-, R- refer to them).

## Problem and goal

A user needs to keep a list of US property records and see the weather at each property at
the time it was added. The goal is a running full-stack application with a GraphQL API that
lets a user list, sort, filter, view, add and delete properties. Adding a property fetches the
current weather and coordinates from Weatherstack exactly once and stores them with the
record. The work is built AI-first, and the AI setup and sessions are part of the deliverable.

## Users

- **User** – anyone who opens the web app or calls the GraphQL API. There are no accounts or
  roles; every user can do everything (D-13, NG-01).
- **Operator** – the person who runs the app locally (e.g. the assessor). Supplies the
  Weatherstack key and reacts to quota errors (D-02, D-14).

## Constraints

Mandated by the brief:

- C-01 Backend in TypeScript on Node.js; frontend in React with TypeScript.
- C-02 The API is GraphQL.
- C-03 Weatherstack `/current` (`https://api.weatherstack.com/current`) is called only inside
  the create-property mutation, never anywhere else.
- C-04 `id` is generated by the backend or database; the format is our choice.
- C-05 `street`, `city`, `state`, `zipCode` are mutation arguments; `weatherData`, `lat`,
  `long` come from the Weatherstack response.
- C-06 Delivered as a public Git repository with a README containing run instructions, plus
  the full AI setup (skills, prompts, agents, MCP config) and the AI session exports.
- C-07 The database is our choice.

## Functional requirements

Conventions used by the acceptance criteria:

- "Error code X" means the GraphQL response has `data` for that field equal to `null` and one
  entry in `errors` whose `extensions.code` is `X` (codes listed in FR-10).
- "The weather adapter" is the single component that calls Weatherstack. In automated tests it
  is a fake; "called N times" refers to that fake.
- "A valid input" is `street: "15528 E Golden Eagle Blvd", city: "Fountain Hills", state: "AZ",
  zipCode: "85268"`, with the fake returning `location.region: "Arizona"`.

### FR-01 List properties  (Must, covers US-01, B-1)

The `properties` query returns the matching properties plus their total number:
`{ items, totalCount }`. Without `limit` it returns **all** matching properties (brief B-1:
"query all the properties"). `limit` and `offset` are optional; `limit` must be 1–100 when given,
`offset` must be ≥ 0 and defaults to 0. This narrows D-10, which had a default page size of 20.

- AC1: Given 3 stored properties, When `properties` is queried with no arguments, Then
  `items` has 3 entries and `totalCount` is 3, and each item exposes `id`, `street`, `city`,
  `state`, `zipCode`, `lat`, `long`, `createdAt` and `weatherData`.
- AC2: Given no stored properties, When `properties` is queried, Then `items` is `[]` and
  `totalCount` is 0 (no error).
- AC3: Given 25 stored properties, When `properties` is queried with no `limit`, Then `items`
  has all 25 entries and `totalCount` is 25.
- AC4: Given 25 stored properties, When queried with `limit: 10, offset: 20`, Then `items` has
  5 entries and `totalCount` is 25.
- AC5: Given any data, When queried with `limit: 0`, `limit: 101` or `offset: -1`, Then the
  response has error code `BAD_USER_INPUT` and no `items`; When queried with `limit: 100` or
  with `offset` and no `limit`, Then no error is returned (the latter returns every match after
  the offset).
- AC6: Given any data, When `properties` is queried, Then the weather adapter is called 0
  times.

### FR-02 Sort by creation date  (Must, covers US-02, B-2)

`properties` takes an optional `sort` argument: `CREATED_AT_DESC` (default, A-07) or
`CREATED_AT_ASC` (D-11). Ties on `createdAt` are broken by `id` in the same direction so that
paging is stable.

- AC1: Given properties P1, P2, P3 created in that order, When queried with no `sort`, Then
  `items` are in order P3, P2, P1.
- AC2: Given the same data, When queried with `sort: CREATED_AT_ASC`, Then `items` are in order
  P1, P2, P3.
- AC3: Given 25 properties, When pages `offset: 0` and `offset: 20` (limit 20) are fetched with
  the same sort, Then together they contain all 25 ids exactly once.

### FR-03 Filter by city, zip code and state  (Must, covers US-03, B-3)

`properties` takes an optional `filter` with optional `city`, `state`, `zipCode`. Given
filters are combined with AND; `totalCount` counts only matching properties (D-06).

- AC1: Given properties in "Fountain Hills" and "Phoenix", When filtered by `city: "fountain"`,
  Then only the "Fountain Hills" property is returned (case-insensitive contains match).
- AC2: Given properties in AZ and CA, When filtered by `state: "az"`, Then only AZ properties
  are returned (input upper-cased, exact match).
- AC3: Given properties with zip codes "85268" and "85260", When filtered by
  `zipCode: "8526"`, Then nothing is returned; When filtered by `zipCode: "85268"`, Then only
  that property is returned (exact match).
- AC4: Given a Phoenix AZ property and a Phoenix (city name) property in another state, When
  filtered by `city: "phoenix", state: "AZ"`, Then only the AZ one is returned.
- AC5: Given filters combined with `sort` and `limit`/`offset`, When queried, Then filtering
  is applied before sorting and paging, and `totalCount` equals the number of matches.
- AC6: Given a filter value that is empty or whitespace only, When queried, Then that filter is
  ignored (treated as not given).

### FR-04 Property details  (Must, covers US-04, B-4, B-7)

The `property(id)` query returns one property with all fields, or `null` if it does not exist
(A-06).

- AC1: Given a stored property, When `property(id)` is queried with its id, Then all fields
  from the data model are returned and equal the stored values.
- AC2: Given no property with id X, When `property(id: X)` is queried, Then `property` is
  `null` and `errors` is absent.
- AC3: Given a stored property, When `property(id)` is queried, Then the weather adapter is
  called 0 times (stored weather is returned, never re-fetched; NG-03).
- AC4: Given an id that is not in the id format, When `property(id)` is queried, Then
  `property` is `null` (not a server error).

### FR-05 Create property  (Must, covers US-05, B-5, B-7, B-N2)

The `createProperty(street, city, state, zipCode)` mutation validates the input, rejects
duplicates, calls Weatherstack once, checks the returned region, and stores the property with
`weatherData`, `lat`, `long` and `createdAt`. The order of steps is: validate → duplicate check
→ weather call → region check → save. A failure at any step saves nothing (D-01).

- AC1: Given a valid input, When `createProperty` runs, Then it returns the new property with a
  generated `id`, the normalized address fields, `lat`/`long` as numbers from
  `location.lat`/`location.lon`, `weatherData` = `{ units: IMPERIAL, current }` where
  `current.raw` equals the response's `current` object and the typed key fields of `current`
  (see Data model) equal the matching response values, and `createdAt` set by the server; and a
  following `property(id)` returns the same data.
- AC2: Given a valid input, When `createProperty` runs, Then the weather adapter is called
  exactly once, with query = the full normalized address
  `"<street>, <city>, <state> <zipCode>, United States"` (D-03) and imperial units (D-08).
  Example: input from AC3 gives `"15528 E Golden Eagle Blvd, Fountain Hills, AZ 85268, United States"`.
- AC3: Given input `street: "  15528  E Golden Eagle Blvd ", state: "az"`, When created, Then
  the stored `street` is `"15528 E Golden Eagle Blvd"` and `state` is `"AZ"` (trimmed, inner
  whitespace collapsed, state upper-cased).
- AC4: Given the fake returns `location.region: "California"` for `state: "AZ"`, When
  `createProperty` runs, Then error code `WEATHER_LOCATION_MISMATCH` is returned, its message
  names both "AZ"/"Arizona" and "California", and the property count is unchanged (D-04, A-12).
- AC5: Given the weather adapter fails (any case in FR-06), When `createProperty` runs, Then
  the matching error code is returned and the property count is unchanged.
- AC6: Given the database rejects the save, When `createProperty` runs, Then error code
  `INTERNAL_SERVER_ERROR` is returned and no partial record exists.

### FR-06 Weather failure handling  (Must, covers US-07, B-5, D-01, D-02, A-08 – A-10)

- AC1: Given Weatherstack returns a usage-limit error (body `error.code` 104 or 429; an HTTP
  429 status is AC4), When `createProperty` runs,
  Then error code `WEATHER_QUOTA_EXCEEDED` is returned with a message telling the operator to
  upgrade the Weatherstack plan or replace the API key.
- AC2: Given Weatherstack returns HTTP 200 with `success: false` and any other error code,
  When `createProperty` runs, Then error code `WEATHER_UNAVAILABLE` is returned (A-10).
- AC3: Given Weatherstack does not answer within 5 seconds, When `createProperty` runs, Then
  error code `WEATHER_UNAVAILABLE` is returned within 6 seconds and the adapter made exactly
  one HTTP request (no retries).
- AC4: Given a network error or a non-2xx HTTP status, When `createProperty` runs, Then error
  code `WEATHER_UNAVAILABLE` is returned.
- AC5: Given a 200 response that lacks `current`, any required (key) field of `current` (see
  Data model), `location.lat`, `location.lon` or `location.region`, or where `lat`/`lon` are not
  numeric, When `createProperty` runs, Then error code `WEATHER_UNAVAILABLE` is returned
  (response validated, R-04). Missing non-key fields do not fail the create.
- AC6: Given the key is missing or invalid, or the plan does not allow the request (body codes
  101, 105 and 403), When `createProperty` runs, Then error
  code `WEATHER_UNAVAILABLE` is returned to the client and a server log entry records a
  configuration error; neither contains the key value (A-09).
- AC7: Given any weather failure, When the error and server logs are inspected, Then no
  string contains the configured key value and any logged URL shows `access_key=[REDACTED]`.

### FR-07 Input validation  (Must, covers US-05, US-07, B-7b – B-7e, A-01 – A-03)

Validation happens before the duplicate check and before any weather call.

- AC1: Given `zipCode` of "8526", "852680", "85268-1234" or "8526A", When `createProperty`
  runs, Then error code `BAD_USER_INPUT` names the `zipCode` field and the weather adapter is
  called 0 times.
- AC2: Given `zipCode: "02108"`, When created, Then the stored and returned `zipCode` is
  `"02108"` (leading zero kept, A-02).
- AC3: Given `state` of "PR", "XX" or "Arizona", When `createProperty` runs, Then error code
  `BAD_USER_INPUT` names `state`; Given "dc" or "ny", Then it is accepted as "DC"/"NY" (A-01).
- AC4: Given `street` or `city` that is empty or whitespace only, or longer than 200 (street)
  / 100 (city) characters after trimming, When `createProperty` runs, Then error code
  `BAD_USER_INPUT` names that field (A-03).
- AC5: Given several invalid fields, When `createProperty` runs, Then one `BAD_USER_INPUT`
  error lists every invalid field.

### FR-08 Duplicate prevention  (Must, covers US-07, D-07)

Two properties are duplicates when their normalized addresses (street + city + state + zip,
trimmed, whitespace collapsed, case-insensitive) are equal.

- AC1: Given a stored valid property, When `createProperty` runs with `street: "15528 e golden
  eagle  blvd", city: "FOUNTAIN HILLS"` and the same state and zip, Then error code
  `PROPERTY_ALREADY_EXISTS` is returned, the weather adapter is called 0 times, and the count is
  unchanged.
- AC2: Given two concurrent `createProperty` calls with the same address and no existing
  record, When both complete, Then exactly one property is stored and the other call returns
  `PROPERTY_ALREADY_EXISTS` (enforced by storage, not only by the pre-check).
- AC3: Given a stored property that is then deleted, When the same address is created again,
  Then it succeeds.

### FR-09 Delete property  (Must, covers US-06, B-6, A-05)

`deleteProperty(id)` permanently removes a property and returns the deleted property's `id`.

- AC1: Given a stored property, When `deleteProperty(id)` runs, Then it returns that `id`, a
  following `property(id)` returns `null`, and `totalCount` drops by 1.
- AC2: Given no property with id X, When `deleteProperty(id: X)` runs, Then error code
  `PROPERTY_NOT_FOUND` is returned.
- AC3: Given any delete, When it runs, Then the weather adapter is called 0 times.

### FR-10 Error contract  (Must, covers US-07, Q-03)

Every expected failure returns a GraphQL error with a stable `extensions.code` and a
human-readable `message`. Unexpected failures return `INTERNAL_SERVER_ERROR` without stack
traces or internal details.

| Code | When | Message must say |
|------|------|------------------|
| `BAD_USER_INPUT` | Argument validation fails (FR-01, FR-07) | Which field(s) and why; `extensions.fields` lists them |
| `PROPERTY_ALREADY_EXISTS` | Normalized address already stored (FR-08) | The address already exists |
| `PROPERTY_NOT_FOUND` | Delete of unknown id (FR-09) | No property with that id |
| `WEATHER_QUOTA_EXCEEDED` | Weatherstack usage limit (FR-06 AC1) | Quota used up; upgrade the plan or replace the API key |
| `WEATHER_UNAVAILABLE` | Any other weather failure (FR-06) | Weather could not be fetched, property not saved, try again later |
| `WEATHER_LOCATION_MISMATCH` | Region ≠ submitted state (FR-05 AC4) | Expected state and the state Weatherstack returned |
| `INTERNAL_SERVER_ERROR` | Anything unexpected | Generic message only |

- AC1: Given each row's trigger, When the operation runs, Then the response carries exactly
  that code.
- AC2: Given an unexpected server exception, When the operation runs, Then the error message
  contains no stack trace, SQL, file path or key value.

## Data model (conceptual)

**Property**

| Field | Type / format | Rules | Source |
|-------|---------------|-------|--------|
| `id` | opaque string, generated | Unique, immutable | backend (C-04) |
| `street` | string | Required; trimmed, inner whitespace collapsed; 1–200 chars | argument |
| `city` | string | Required; trimmed, inner whitespace collapsed; 1–100 chars | argument |
| `state` | string, 2 letters | One of 50 state codes + DC; stored upper-case | argument |
| `zipCode` | string, 5 digits | `^[0-9]{5}$`; stored as text | argument |
| `lat` | decimal number | −90…90; from `location.lat` | Weatherstack |
| `long` | decimal number | −180…180; from `location.lon` | Weatherstack |
| `weatherData` | WeatherData | Required; `{ units, current }`, `current` stored whole as received | Weatherstack (D-09, B-7f) |
| `createdAt` | timestamp, UTC, ISO 8601 in the API | Set by backend at save | backend (A-07) |

Uniqueness: normalized address (lower-cased street + city + state + zip) is unique (D-07).
Properties are immutable after creation (A-04).

**WeatherData** — follows the brief literally (B-7f: "object containing 'current' property"):
`weatherData { units, current { ... } }`. The stored snapshot is `{ units, current }` with
`current` exactly as Weatherstack returned it.

| Field | Type | Required | Priority |
|-------|------|----------|----------|
| `units` | enum `IMPERIAL` (°F, mph, in) | yes (D-08) | Must |
| `current` | CurrentWeather | yes | Must |

**CurrentWeather** (fields from Weatherstack `current`, camelCased in the API)

| Field | Type | Required | Priority |
|-------|------|----------|----------|
| `raw` | JSON scalar: the whole `current` object as received | yes | Must |
| `temperature`, `feelsLike` | integer | yes | Must |
| `weatherDescriptions`, `weatherIcons` | list of strings | yes | Must |
| `windSpeed` | integer | yes | Must |
| `windDir` | string | yes | Must |
| `humidity` | integer | yes | Must |
| `observationTime`, `weatherCode`, `windDegree`, `pressure`, `precip`, `cloudCover`, `uvIndex`, `visibility`, `isDay` | as in Weatherstack (`isDay` boolean from "yes"/"no") | no | Should (typed fields); always available in `raw` |
| `astro` | sunrise, sunset, moonrise, moonset, moonPhase, moonIllumination | no | Should (typed object); available in `raw` |
| `airQuality` | co, no2, o3, so2, pm2_5, pm10, usEpaIndex, gbDefraIndex | no | Should (typed object); available in `raw` |

"Required" means a create fails with `WEATHER_UNAVAILABLE` if the field is missing (FR-06 AC5).
The Must key fields are the ones the details page must show (FR-12 AC1). Exact nullability of
non-key fields is unknown from one sample (OQ-03), so they stay optional.

## External integrations

### Weatherstack current weather

- **Endpoint:** `GET {WEATHERSTACK_BASE_URL}/current`. Default base URL
  `https://api.weatherstack.com` (brief); configurable (A-11, R-02).
- **Called from:** the create-property mutation only, once per successful validation and
  duplicate check (C-03). Never from queries, delete, seed scripts outside the mutation, or
  automated tests.
- **Request parameters:**
  - `access_key` – from `WEATHERSTACK_KEY`; never logged or returned (redacted as
    `[REDACTED]`).
  - `query` – the full normalized address `"<street>, <city>, <state> <zipCode>, United States"`,
    built from the validated, normalized fields (D-03).
  - `units` – `f` (D-08).
- **Response fields used:**
  - `location.lat`, `location.lon` – strings holding decimals (sample:
    `"33.609"`, `"-111.729"`); parsed to numbers → `lat`, `long`.
  - `location.region` – full state name (sample: `"Arizona"`); compared with the name of the
    submitted state code (D-04, A-12), case-insensitive, trimmed.
  - `current` – stored whole as `weatherData.current` next to `units` (B-7f); key fields are
    validated and typed (shape: `docs/samples/weatherstack-current.json`).
  - `success`, `error.code`, `error.type`, `error.info` – failure detection (A-10).
- **Error cases:**

  | Case | Detected by | Our code |
  |------|-------------|----------|
  | Usage limit reached | `success: false`, `error.code` 104 (`usage_limit_reached`) — docs | `WEATHER_QUOTA_EXCEEDED` |
  | Monthly allowance reached | `error.code` 429 (`too_many_requests`) — docs | `WEATHER_QUOTA_EXCEEDED` |
  | Missing/invalid key | `error.code` 101 (`unauthorized`; older docs: `missing_access_key` / `invalid_access_key`) — docs | `WEATHER_UNAVAILABLE` + config log |
  | Plan does not support the function or HTTPS | `error.code` 403 (`forbidden`) — docs | `WEATHER_UNAVAILABLE` + config log |
  | HTTPS not allowed on plan (legacy) | `error.code` 105 (`https_access_restricted`) — older docs only (R-02) | `WEATHER_UNAVAILABLE` + config log |
  | Location not found | `error.code` 615 (`request_failed`) — docs | `WEATHER_UNAVAILABLE` |
  | Any other `success: false` | `error` present | `WEATHER_UNAVAILABLE` |
  | Rate limit (calls in quick succession) | HTTP 429 status (seen 2026-10-07), whatever the body | `WEATHER_UNAVAILABLE` |
  | Timeout (> 5 s), network error, non-2xx | client | `WEATHER_UNAVAILABLE` |
  | Body fails validation | schema check | `WEATHER_UNAVAILABLE` |
  | Region ≠ submitted state | region check | `WEATHER_LOCATION_MISMATCH` |

- **Limits:** free plan about 100 calls/month — UNVERIFIED; free plan may reject HTTPS —
  UNVERIFIED (R-02). One attempt per create, 5 s timeout, no retries (A-08).
- **Verified so far (manual calls, 2026-10-07, `units=f`, HTTPS):**
  - A full-address query is accepted, but Weatherstack ignores the street and resolves to the
    city (`request.type: "City"`). The brief's address gives `Fountain Hills`, `Arizona`,
    `33.609` / `-111.729` (the brief's example values). A non-existent street in the same town
    gives the same result; a Texarkana, AR address gives `region: "Arkansas"`.
  - HTTPS works with the project's key.
  - Two calls within about a second returned HTTP 429.
  - Response shape: `docs/samples/weatherstack-current.json` (the brief's address, imperial).
  - Error codes (S-02 plan, from the archived `weatherstack.com/documentation`, 2024 snapshot,
    *API Error Codes*; the live docs render only on the client): the error body is
    `{ success: false, error: { code, type, info } }`; 101 `unauthorized`, 104
    `usage_limit_reached`, 429 `too_many_requests` (monthly allowance), 403 `forbidden` (plan
    or HTTPS), 615 `request_failed`. 105 is not in the current table. Classification uses only
    `code`, never `type`, and `info` is never logged or returned. 104 and 429 are not triggered
    for real.
  - DC region (R-03, S-02 Phase 2): a `createProperty` for `1600 Pennsylvania Ave NW`,
    `Washington`, `DC`, `20500` through `pnpm dev` succeeded, so Weatherstack's `region` for
    DC matches `"District of Columbia"`. No alias is needed.
  Everything else in this section marked UNVERIFIED is checked when the adapter is built.

## Non-functional requirements

- NFR-01 **Secrets:** the Weatherstack key appears in no source file, commit, log line, API
  response or error message. Logged URLs show `access_key=[REDACTED]`. Testable by asserting
  the key string is absent from captured logs and responses in failure tests.
- NFR-02 **No real third-party calls in tests:** the automated test suite completes with
  outbound network access to Weatherstack blocked.
- NFR-03 **Timeouts:** the create mutation returns within 6 s when Weatherstack hangs
  (5 s timeout + overhead).
- NFR-04 **Type safety:** strict TypeScript compile with zero errors and no explicit `any`
  (enforced by the type check and lint commands).
- NFR-05 **Input validated at the boundary:** mutation/query arguments, environment config and
  the Weatherstack response are validated before reaching business logic.
- NFR-06 **Layering:** API handlers → business services → persistence / third-party adapters;
  no layer skips the one below (checked in review).
- NFR-07 **Testability:** every Must FR has automated tests; the weather adapter is replaceable
  by a fake through configuration or dependency injection.
- NFR-08 **Data integrity:** a create either stores a complete record (all required fields
  non-null) or nothing.
- NFR-09 **Usability:** every UI view has explicit loading, empty and error states (D-12);
  every API error code in FR-10 has a dedicated UI message.
- NFR-10 **Reproducibility:** a fresh clone starts with one command plus a `.env` holding only
  the key (FR-14).

## Non-goals

- NG-01 Authentication, authorization and user accounts; every user has full access (D-13).
- NG-02 Editing a property after creation; there is no update mutation (A-04).
- NG-03 Refreshing or re-fetching weather after creation (C-03).
- NG-04 Our own geocoding or address verification beyond the state region check (D-04).
- NG-05 Addresses outside the 50 states + DC, including territories and ZIP+4.
- NG-06 Soft delete, audit history, undo.
- NG-07 Public deployment or hosting; the app runs locally.
- NG-08 Sorting by anything other than creation date; full-text search.
- NG-09 Showing historical or forecast weather.
- NG-10 Metric units or a unit toggle.
- NG-11 Mobile apps or offline support; the web UI targets current desktop browsers.

## Success criteria

The scope is complete when a reviewer can:

1. Clone the repo, add a key to `.env`, run the one documented command and reach the UI
   (FR-14).
2. Create a property from a Zillow address and see its key weather fields, `lat` and `long`
   on the details page (FR-05, FR-12 AC1).
3. List all, sort both ways, filter by city/state/zip, view and delete properties in the UI and
   through the GraphQL API, and page with `limit`/`offset` through the API (FR-01 – FR-04,
   FR-09, FR-11 Must ACs).
4. Trigger a validation error, a duplicate and (with a fake or exhausted key) a weather error
   and see the specific messages (FR-06 – FR-08, FR-10, FR-13).
5. Run lint, type check and the test suite with all passing and no real Weatherstack calls
   (NFR-02, NFR-04, NFR-07).
6. Find the AI setup, `context/` artifacts and session exports in the repo (FR-15).
7. Every Must FR has passing automated tests that map to its acceptance criteria.

Should items (FR-11 AC3a and AC4, FR-12 AC6, typed non-key `current` fields including `astro`
and `airQuality`) are not needed for completion; they are tracked in the roadmap's *Later*.
